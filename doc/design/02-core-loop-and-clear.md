# 02. 플레이 흐름·클리어·실패 처리

> 기준: V8.1.0 / main `5ea02af8c748bfc1207a06932154407bbf3a0232`. 이 문서는 현행 구현을 정리합니다. 기획 의도·제작 기준·후속 검토는 별도로 표시합니다.

## 기본 흐름

`방 진입 → 지형과 연결 관찰 → 조작 대상 선택 → 위치/형태/빛/길이 조절 → 환경 변화 확인 → 출구 도달 → 조작 종료 → 클리어`

막히면 다른 위치·형태·빛축을 시도하거나 되돌린다. 상자를 죽이고 다시 시작시키는 구조가 아니라, 불가능한 이동·변형을 안전한 경계에서 멈추는 구조다.

## 상태별 동작

| 상태 | 현재 동작 |
|---|---|
| 최초 진입 | 저장을 읽고 유효한 방을 복원한다. 유효한 `?stage=N`이 있으면 해당 방의 초기 상태로 진입한다 |
| 방 초기화 | 상자, 광원, 발판 길이, 센서, 장치 상태를 만들고 초기 접촉도 계산한다 |
| 입력 시작 | `Game.begin()`으로 조작 전 상태를 보관한다 |
| 입력 중 | 이동·변형의 중간 경로를 검사하고 센서와 문/다리를 갱신한다 |
| 입력 종료 | 달라진 상태가 있으면 기록하고 `canWin`을 평가한다 |
| 클리어 | 완료 ID를 저장하고 이 방의 `meaning`과 다음 방 버튼을 표시한다 |
| 마지막 방 완료 | 모든 방 선택 화면으로 돌아가는 버튼을 표시한다 |
| 다시 | 해당 방만 초기화한다. 완료 ID와 정밀 설정을 지우는 전체 초기화가 아니다 |

## 클리어의 정확한 조건

`canWin = insideGoal && !collides`다. 출구는 중심 좌표와 가로·세로 크기의 직사각형이고, 상자의 사각형 전체가 그 안에 들어가야 한다. 그림자가 출구에 들어간 것, 상자가 일부만 겹친 것, 모든 버튼을 눌렀다는 사실만으로 완료되지 않는다.

`Game.end()`의 **변경이 있는 조작 종료**에서 승리 상태가 확정된다. 보통 손/마우스를 떼거나 키보드 조작을 마칠 때다. 프리셋 버튼 조작도 한 번의 종료를 만든다. 정확한 엔진 계약은 '포인터를 반드시 떼야 한다'보다 '트랜잭션 종료 시 판정'이다.

숫자 인장 순회, SW 방문 순서, 모든 센서 활성화 여부는 승리 체크리스트에 없다. UI의 다음 장치 안내는 현재 닫힌 장치를 설명할 뿐 숨겨진 정답 순서를 강제하지 않는다.

## 실패 및 복구

| 상황 | 결과 |
|---|---|
| 벽·닫힌 문·빈 공간으로 이동 | 통과하지 않고 가능한 위치까지 이동 |
| 변형 중 벽 또는 물가에 걸림 | 허용되는 중간 형태까지만 변화 |
| 발판을 줄여 상자 지지가 사라짐 | 상자를 받치는 길이 경계에서 정지 |
| 그늘판에서 벗어남 | 연결 장치가 비활성화. 이미 열린 장치와 상자가 겹치면 안전 유지 |
| 조작을 잘못 선택함 | 대상 변경 또는 되돌리기 |
| 길이 막혀 현재 상태에서 풀기 어려움 | 되돌리기/다시 사용. 자동 막힘 감지 기능은 없음 |

되돌리기는 최근 100개 변경 기록까지다. 위치뿐 아니라 장치·광원·선택 대상도 복구한다. 횟수 제한이나 실패 패널티는 없다.

## 기획상 수용 기준

시작 상태는 벽과 충돌하거나 출구에서 시작하지 않게 작성한다. 출구 근처를 나갔다가 재진입하는 것만으로 의도한 문제를 생략할 수 있는지 확인한다. 단, 기존 규칙을 모두 지킨 다른 해법은 인정한다. 문과 다리로 생긴 실제 접근 조건을 설계하고 임의 방문 조건으로 보정하지 않는다.
