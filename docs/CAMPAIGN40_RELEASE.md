# V8.0.0 — 40스테이지 구현 및 검증

## 범위

승인한 확장 기획안은 `Shadow_Puzzle_40Stage_Expansion_Plan.md`에 원문 그대로 보존합니다. 1–12 학습, 13–16 조합, 17–24 본격 퍼즐, 25–32 응용, 33–40 최종 구간입니다. 신규 센서 종류, 회전/자유이동 발판, 추, 타이머, 적, 횟수 제한은 없습니다.

기존의 14개 방을 새 캠페인에 맞춰 재배치했고 그 지형 ID는 유지했습니다. 나머지 26개 방은 새 ID와 별도의 명시적 지형·해답을 갖습니다. 돌벽·물길·문을 샘플링한 실루엣은 회전·반사를 포함해 같은 것이 없는지 자동 검사합니다. 이것이 체감 반복감까지 없다는 보장은 아니므로 각 방의 발상은 플레이테스트로 추가 평가합니다.

## 중요한 구현 원칙

- 17: 출구의 세로 형태와 발판의 연결 길이/폭을 함께 준비합니다. 최대 길이가 항상 해답이 아닙니다.
- 26: A를 건너온 뒤 줄여 넓은 작업면을 확보합니다. 같은 경로에서 두 발판을 최대 길이로 고정하면 형태 변경이 막히는 음성 대조 검사도 둡니다.
- 29: 상자 중심을 옮기지 않고 형태로 그림자 끝을 장치에 닿게 합니다.
- 33: 문마다 기존 센서 하나를 연결합니다. 어느 센서를 비활성화하더라도 해당 해답 경로가 막히는지 검사합니다. 새로운 AND/OR 회로는 없습니다.
- 39: 준비 순서가 다른 두 해답 모두 실제 다리를 펼치고 출구에 도달합니다.
- 40: ‘발판 A/B’와 ‘빛 A/B’는 별도 선택 대상으로 명확하게 표시합니다.

현실 물리와 그림자 투영, 발판 면적 보존, 문 끼임 방지, 연속 충돌 판정은 V7.1 그대로입니다. 코어 변경은 재배치된 방의 저장을 `levelId`로 찾는 부분뿐입니다. 센서·지원 판정을 느슨하게 해서 테스트를 통과시키지 않았습니다.

## 기획 좌표 조정

기획안은 좌표가 없는 의도 문서입니다. 실제 제작에서는 문턱/물가에서 형태 변경에 필요한 공간을 확보하고, 통로의 회전·반사 반복을 피했습니다. 특히 13번 해답의 변형 위치는 천장에서 떨어진 작업면으로 이동하고, 38번 귀환 경로는 다리 가장자리 대신 가운데를 지납니다. 40번의 마지막 발판은 작은 입력 오차가 있어도 착지 후 변형할 수 있도록 폭의 여유를 확보했습니다. 34번 A는 건너는 길이 아닌 작업 자리이므로 도달 가능한 작업 지점을 표시하고, 불가능한 양쪽 강둑 연결을 요구하는 안내를 내보내지 않습니다. 판정을 우회하는 숨겨진 방문 조건은 없습니다.

## 검증

- Node 검사: 기존 78개 회귀 항목 + 캠페인/저장 이전 59개 = 137개.
- 40개 방은 실제 코어 API를 통한 입력 경로를 가지며, 각 조작 후 충돌·저장 복원까지 검사합니다.
- 39번은 두 번째 준비 순서도 검사합니다.
- 이전 19개 방 회귀 검사는 **현재 엔진 + 보존한 V7 방 데이터**로 계속 실행합니다. 이전 UI 검사는 별도 QA 빌드로 유지하고, 배포 빌드에는 40개 방만 포함합니다.
- 활성 40개 방 브라우저 검사는 버튼·패드·키보드 범위 입력을 사용하며, 실행 중 게임 상태를 직접 바꾸지 않습니다.
- 화면 검사: 320×568, 360×640, 393×852, 844×390, 768×1024, 1365×768, 1920×1080. 2광원+2발판 복합 방의 선택 버튼, 화면 회전, 저장/새로고침, 저장 차단, JS 차단, 실제 Chromium 터치 입력을 포함합니다.
- 고정 광원의 축은 실제 입력으로 도착한 위치에서 형성됩니다. 브라우저 검사에서는 CSS 픽셀 반올림으로 생긴 작은 차이(최대 12 월드 단위)를 실제 축에 투영해 조작합니다. 게임의 물리·클리어 판정은 바꾸지 않고 최종 완료를 실제 UI에서 확인합니다.

로컬 컨테이너는 URL 탐색이 정책상 차단되어 `--fixture`(메모리 HTML)로 검사합니다. 이 모드는 HTTP/저장 원점 검증이 아니며, CI에서는 사용하지 않습니다. GitHub Actions는 세 엔진에서 실제 HTTP로 전체 캠페인을 검사한 다음 배포하고, 공개 HTTPS에서 커밋과 대표 문제를 다시 검사합니다.

## 남은 확인

검토는 작성자 자체 검토와 자동화 테스트입니다. 별도 검토자/실기기 테스트로 간주하지 않습니다. 실제 iOS/Android 터치감, 장기 플레이 성능, ‘17부터 어렵다’는 체감과 후반 문제의 반복감은 실기기 플레이테스트가 필요합니다.
